# bison-db v1.1.0: failure-path hardening

v1.1.0 fixes how the store behaves when things go wrong: a second handle on a
live file, damaged records, a failed compaction, deleted ids after compaction,
and hostile documents. The API changes are additions only, the minimum Rust
version stays 1.85, and the on-disk format stays at version 1: every file
written by 0.2.0 through 1.0 opens unchanged, and files written by 1.1 open in
1.0.

## What changed

### One handle per file

`Db::open` now takes an exclusive lock on the store and a second open of a live
store, from the same process or another one, fails with the new
`Error::Locked`. Before, two handles could open the same file and overwrite each
other's acknowledged writes.

The lock is a sibling `<path>.lock` file. File locking in `std`
(`File::try_lock`) needs Rust 1.89, above this crate's MSRV, and the crate adds
no dependency and no `unsafe`, so it uses what `std` offers on each platform:

- **Windows:** the lock file is held open with a share mode of zero. The OS
  enforces it and releases it when the process exits, so a crash never leaves a
  stale lock.
- **Unix:** the lock file is created with `create_new` and names its holder
  (process id, process start time, host, PID namespace). On Linux a lock whose
  holder no longer exists, or whose process id now belongs to a process with a
  different start time, is replaced automatically. Where the holder cannot be
  checked (another host, another PID namespace, or a Unix without `/proc` such
  as macOS), the lock is honoured; on macOS and the BSDs a lock left by a
  crashed process is removed by hand.

### Damage before the end of the log

A torn final record, which is what a crash during a write leaves, is still cut
off on open, and the new `Db::discarded_bytes` reports how many bytes were
removed. Damage anywhere before the end is now always reported as
`Error::Corrupt`, with the file left exactly as it was. Before, a damaged length
field could make `open` truncate every later record and return `Ok`.

The new `RecoveryMode::Salvage` (`DbOptions::recovery`) opens a damaged file
anyway: it keeps every record that still verifies, saves a byte-for-byte copy of
the damaged file as `<path>.damaged`, and rewrites the store so it opens cleanly
afterwards.

### Compaction

- If the rename that swaps the compacted file in fails, the handle now keeps
  using the original file and the temporary file is removed. Before, later
  writes went to the temporary file, which the next open deleted.
- Compaction keeps the id counter, so a deleted id is never handed out again
  after compaction and reopen. It does this by keeping one DELETE record for the
  highest id, a record kind format version 1 already has.
- Each record is copied byte for byte after its checksum verifies, so damage is
  reported instead of being stamped with a fresh checksum.

### Hostile input

- Decoding a document is linear in its field count; it was quadratic. The serde
  path and `FromIterator` are linear too.
- New limits, checked before work: `MAX_DOCUMENT_FIELDS` (65,536 fields per
  document or object) and `MAX_NESTING_DEPTH` (256 levels). Writing past them
  fails with `Error::ValueTooLarge`; a stored record nested deeper is
  `Error::Corrupt`; serde deserialization fails past either.
- Decoders reserve memory for at most a small fixed number of elements before
  they arrive, and the serde visitors cap the size hint a format reports, so a
  length field can no longer request far more memory than the input holds.

### Writes and reads

- `insert`, `update` and `delete` change in-memory state only after the record
  is written (and synced under `SyncPolicy::Always`), so a failed write leaves
  the store and its secondary indexes as they were.
- A failed `fsync` makes the store refuse further writes until it is reopened,
  since the state of the disk is then unknown.
- `get` verifies the record's checksum on every read, as the docs said it did.
- Replay reads the log through a 1 MiB buffer instead of two syscalls per
  record, so opening a large store is faster.
- Unindexed `find` and `range` return results in the same order as the indexed
  path (ascending id; value then id).
- `DbOptions::sync_policy` and `DbOptions::recovery_mode` are the getters;
  `DbOptions::build_sync_policy` is deprecated.
- The write buffer no longer keeps the size of the largest document forever.

### Documentation

README, API.md, FORMAT.md and PERFORMANCE.md now describe the store as it is:
single-operation atomic, crash-safe appends rather than ACID transactions,
property tests rather than fuzzing, the one-handle rule, the recovery rules, and
the platform the read-speed comparison was measured on. The crate has no runtime
dependencies; the README no longer says it builds on other storage crates.

## Upgrading

Nothing to change for code that compiles against 1.0, except a deprecation
warning for `build_sync_policy`. Code that opened the same file twice, which
could lose data, now gets `Error::Locked`. A store a 1.0 build opened with
silent truncation may now be refused as `Error::Corrupt`; open it once with
`RecoveryMode::Salvage` to recover what verifies.
